# Esquema PostgreSQL de SistemaGym

## Alcance y advertencia

`01_sistemagym_schema.sql` es una traducción del esquema maestro versionado en
`docs/sql/mysql/01_sistemagym_estructura_completa.sql`. Define las mismas 25
tablas; incluye `entradas_diarias`, `socios.dni`, claves, índices y checks: los
48 checks de negocio del maestro más 64 checks para conservar la
no-negatividad de columnas `BIGINT UNSIGNED`. Las tres columnas derivadas se
conservan como columnas generadas `STORED`.

Este archivo **no acredita** que `sistemagym_definitiva` tenga exactamente ese
esquema. No ejecutar en Supabase real hasta comparar metadatos del origen,
revisar preflight y contar con respaldo y autorización expresa. El SQL del
archivo adjunto de `operaciones_pago_idempotentes` tiene una condición menos
estricta: este DDL mantiene la invariancia endurecida del maestro para los tres
estados, incluido `REJECTED`.

## Orden de aplicación

El script `01_sistemagym_schema.sql` realiza este orden, en una única ejecución
contra el esquema `public` de una base nueva:

1. Crear/verificar el esquema `extensions` e instalar/verificar `unaccent` 1.1
   allí (`CREATE EXTENSION ... WITH SCHEMA extensions`). En Supabase, comprobar
   primero que la extensión habilitada está en ese esquema; `IF NOT EXISTS` no
   mueve una extensión que ya estuviera instalada en otro esquema.
2. Crear la colación ICU `sistemagym_ai_ci` (`und-u-ks-level1`, no determinista).
3. Crear la función trigger `sistemagym_set_fecha_actualizacion`.
4. Crear las 25 tablas, con columnas generadas, checks, PK/FK y restricciones
   únicas.
5. Crear los índices explícitos.
6. Adjuntar los triggers de actualización automática de timestamps.
7. Arrancar la aplicación con `ddl-auto=validate`.

El archivo solo crea estructura: no carga roles, usuarios ni datos reales. Si se
necesitan datos, cargarlos mediante un seed separado, ficticio, revisado y solo
después de completar el preflight de la fuente.

No usar el esquema MySQL `sistemagym_definitiva` para pruebas de escritura. No
ejecutar este archivo sobre una base que ya tenga objetos sin un plan aditivo y
un inventario de diferencias.

## Equivalencias relevantes

- `AUTO_INCREMENT` → `GENERATED BY DEFAULT AS IDENTITY`; `UNSIGNED` → entero
  PostgreSQL más checks no negativos. PostgreSQL no tiene `BIGINT UNSIGNED`; el
  límite superior queda restringido a `Long.MAX_VALUE`, aceptado para el modelo
  Java.
- `DATETIME` y la mayoría de `TIMESTAMP` se traducen a `timestamp without time
  zone`. Campos de sesión Java `Instant` usan `timestamp with time zone`. Los
  campos UTC sin zona se almacenan como hora local UTC por contrato de la
  aplicación; la fecha operativa del gimnasio se deriva en `America/Lima`.
- `TINYINT(1)` → `boolean`.
- `LONGTEXT` → `text`, y `JSON` se conserva como `json`.
- `REGEXP`/`REGEXP_LIKE` → operador regex PostgreSQL `~`.
- `GET_LOCK`/`RELEASE_LOCK` no forman parte del DDL: el backend los reemplaza
  por advisory locks PostgreSQL con alcance transaccional o de sesión, según el
  proceso; no se debilitan los bloqueos.
- PostgreSQL no implementa `ON UPDATE CURRENT_TIMESTAMP` como cláusula de
  columna. Triggers `BEFORE UPDATE` reproducen la actualización para SQL directo
  y respetan el valor nuevo explícito que asignan los callbacks JPA.
- `sistemagym_ai_ci` es una colación ICU no determinista (`und-u-ks-level1`)
  asignada a columnas textuales que en MySQL usan `utf8mb4_0900_ai_ci`. Las
  columnas MySQL `ascii_bin` mantienen colación binaria `C` en PostgreSQL.
  Se requiere ICU en PostgreSQL y la extensión `unaccent` en el esquema
  `extensions`; la búsqueda la llama como `extensions.unaccent(...)`, sin
  depender de `search_path`.

## Validación local aislada

La prueba automatizada PostgreSQL usa Testcontainers y crea una instancia
desechable. Requiere Docker activo. No apunta a Supabase ni a MySQL local.

## Comparación con `sistemagym_definitiva` (solo metadatos)

Se ejecutó `SHOW CREATE TABLE` para las 25 tablas de
`sistemagym_definitiva`; son consultas de metadatos y no leyeron filas de
negocio ni modificaron la base. Las definiciones confirman las restricciones e
índices inspeccionados, `utf8mb4_0900_ai_ci` por defecto, excepciones `ascii_bin`
y las cláusulas efectivas `ON UPDATE`.

Diferencias funcionales confirmadas o pendientes de resolución:

- MySQL usa `BIGINT UNSIGNED` para identificadores y referencias; aquí se usa
  `BIGINT` con checks no negativos. PostgreSQL no tiene `BIGINT UNSIGNED`: el
  rango positivo llega solo a `9223372036854775807`, frente a
  `18446744073709551615` en MySQL. El mapeo conserva la no-negatividad, no todo
  el rango. Se acepta el límite de `Long` en PostgreSQL y se mantienen los
  checks no negativos. No se leyeron filas reales: verificar que todos los IDs y
  referencias a migrar sean `<= 9223372036854775807` queda como preflight
  obligatorio sobre una copia segura.
- `planes.duracion_dias` es `INT UNSIGNED` en MySQL y `INTEGER` más `> 0` en
  PostgreSQL; el límite superior PostgreSQL es menor (y también coincide con el
  tipo Java `Integer`).
- MySQL tiene `ON UPDATE CURRENT_TIMESTAMP` en
  `configuraciones.fecha_actualizacion` y
  `operaciones_pago_idempotentes.fecha_actualizacion(6)`. Los callbacks JPA
  actualizan esos campos en escrituras de la aplicación, pero no equivalen a la
  regla de base de datos para escrituras SQL directas. Los triggers agregados
  actualizan ambas columnas y respetan el valor explícito de JPA; están cubiertos
  por integración.
- `SHOW CREATE TABLE` confirma que las columnas textuales ordinarias heredan
  `utf8mb4_0900_ai_ci`; `sesiones_refresh.token_hash`,
  `sesiones_refresh.csrf_hash` e `invitaciones_usuario.token_hash` especifican
  `ascii_bin`. La colación ICU PostgreSQL reproduce la insensibilidad a
  mayúsculas y acentos en comparaciones/UNIQUE; `C` conserva los campos binarios.
  La equivalencia Unicode exacta puede variar con las versiones ICU/Unicode del
  servidor. Se prueban comparaciones ASCII, acentuadas, unicidad y búsqueda
  global con `unaccent`. Antes de
  importar, comprobar colisiones de datos bajo esta colación; no se leyeron filas.
- `SHOW CREATE TABLE` confirma que las tres columnas calculadas son `STORED` y
  que las expresiones coinciden con PostgreSQL. Se conservan sus claves únicas
  de sesión abierta, documento/fecha y pase/día; la integración verifica la
  generación y el rechazo de duplicados.
- `TINYINT(1)` pasa a `BOOLEAN`; es una equivalencia de dominio deliberada, no
  igualdad del tipo físico.

Las diferencias físicas `UNSIGNED`/signed y `TINYINT(1)`/`BOOLEAN` son decisiones
explícitas del mapeo al modelo Java/PostgreSQL. Verificar valores reales y
colisiones case/accent-insensitive sigue pendiente porque no se consultaron filas.

## Pendiente para corte de producción

  duplicados y colisiones case/accent-insensitive antes de importar datos.
- Definir estrategia de exportación/importación de datos y secuencias/identity;
  validar huérfanos, duplicados y valores fuera de rango en una copia segura.
- Probar URL Supabase y TLS exclusivamente con variables protegidas del
  entorno de despliegue, sin guardar secretos en este repositorio.
